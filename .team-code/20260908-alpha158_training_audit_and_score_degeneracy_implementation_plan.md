### 1.3 Findings — where the repo deviates from Qlib's documented/intended pattern

**1.3.1 — `--num_boost_round` CLI override is a repo-specific mechanism with no Qlib precedent, and it mutates the task config that gets logged and trained**

- Qlib's canonical pattern (README, `qrun`, the benchmark YAMLs) trains **directly from the YAML-declared hyperparameters**. There is no documented Qlib convention for a CLI flag that overrides a single hyperparameter of an already-loaded task config immediately before `task_train` is invoked.
- This repo's runner adds exactly that: `build_parser()` exposes `--num_boost_round` (`type=int, default=None`, help text: *"Override number of boosting rounds for quick testing."*), and `train_alpha158_model()` applies it unconditionally: `config["task"]["model"]["kwargs"]["num_boost_round"] = num_boost_round` (line ~718) before calling `task_train`.
- This is not inherently wrong as a *developer convenience* — but nothing downstream distinguishes a "quick testing" run from a production run. Steps 6–10 of `train_alpha158_model()` unconditionally overwrite the canonical production artifacts (`models/lightgbm/alpha158_russell1000_latest.pkl`, `.txt`, `_meta.json`, and `output/scores/alpha158_russell1000_latest.parquet`/`.csv`) regardless of whether `--num_boost_round` was passed, and regardless of its value. **Part 2 below shows this override is the concrete, confirmed mechanism behind the current 7-distinct-value score collapse** — a quick-test invocation's output silently became the production artifact.
- Qlib's own `LGBModel.__init__` defaults to `num_boost_round=1000` with `early_stopping_rounds=50` (`qlib/contrib/model/gbdt.py:19`) — i.e., Qlib's documented, intended behavior is to let early stopping on the validation set determine the actual tree count, not to hard-fix it at an arbitrarily small integer.

**1.3.2 — IC/RankIC are computed twice, via two different methods, and only one of them is Qlib's own mechanism**

- `SigAnaRecord.generate()` (Qlib's own, `qlib/workflow/record_temp.py:259-268`) already computes `IC`, `ICIR`, `Rank IC`, `Rank ICIR` via `qlib.contrib.eva.alpha.calc_ic` and logs them to the MLflow recorder (`recorder.log_metrics`) as part of `task_train`'s normal `record` pipeline — confirmed present and populated in `mlruns/306366047040812909/145fb75192024a80b0ad8e1f95c366f0/metrics/{IC,ICIR}`.
- `train_alpha158_lightgbm.py` **also** computes its own IC/RankIC/ICIR independently, in `calculate_ic_metrics()`, via a hand-rolled per-date `pandas.Series.corr(method="pearson"/"spearman")` loop over `pred.pkl`/`label.pkl` reloaded from the recorder. This is a parallel, not-quite-equivalent computation (Qlib's `calc_ic` groups by date and computes Pearson/Spearman correlation too, so the two *should* converge, but they are two independently maintained code paths computing the same thing, and only the custom one is ever printed to the banner or written to `_meta.json`).
- Neither code path is currently asserted against any threshold — both are strictly informational/logged. This is a direct gap flagged for Part 3.

**1.3.3 — No model/score quality gate at all before overwriting production artifacts**

- Qlib itself provides no built-in "reject this model" gate (that responsibility is left to the caller), so this is not strictly a *deviation* from a documented Qlib convention — but it is a gap relative to the standard production ML pattern Qlib's own `SigAnaRecord`/`PortAnaRecord` infrastructure is clearly designed to support (compute IC/backtest metrics *before* you'd promote a model). This repo's runner computes the metrics (both via `SigAnaRecord` and its own `calculate_ic_metrics`) but never branches on them — every run reaches steps 6–10 and overwrites `_latest.*` unconditionally, whether it trained 1 boosting round or 1000. This is the same gap the 2026-09-05 council review already identified for the num_leaves=1 bug and it evidently was not closed, since it just recurred in a different shape (num_boost_round=1 instead of over-regularization).

### 1.4 Part 1 — Concrete, Scoped Next Steps

1. **Gate `--num_boost_round` (and any future "quick test" override) behind an explicit, unmissable flag** — e.g. rename to `--dry_run_num_boost_round` and require a companion `--i-understand-this-is-not-production` (or simply refuse to write to `models/lightgbm/alpha158_russell1000_latest.*` / `output/scores/alpha158_russell1000_latest.*` at all when the override is active, writing instead to a `models/lightgbm/_smoketest/` path). Scope: `scripts/train_alpha158_lightgbm.py`, `build_parser()` and `train_alpha158_model()` only.
2. **Consolidate IC/RankIC computation onto Qlib's own `SigAnaRecord`/`calc_ic` output** instead of maintaining a second hand-rolled implementation — read `ic.pkl`/`ric.pkl` (already saved as recorder artifacts by `SigAnaRecord`) or the recorder's logged `IC`/`ICIR`/`Rank IC`/`Rank ICIR` metrics directly, and keep `calculate_ic_metrics()` only if it needs to report something `SigAnaRecord` genuinely does not (e.g. its recomputation is currently used to feed the banner/meta.json before `SigAnaRecord`'s objects are guaranteed flushed — verify ordering before deciding to drop it). Scope: `scripts/train_alpha158_lightgbm.py::calculate_ic_metrics` and its two call sites; read (not modify) `qlib/workflow/record_temp.py` to confirm artifact availability ordering first.
3. **Add the promotion gate described in Part 3** (see below) as the mechanism that actually prevents an under-trained or degenerate run from overwriting `_latest.*` — this closes 1.3.3 concretely rather than just documenting it.
4. Document, in `train_alpha158_lightgbm.md` (the Part-2-required per-function spec doc), that `infer_processors=[]` / `learn_processors=[DropnaLabel, CSZScoreNorm(label)]` is inherited Qlib default behavior, not a repo override — so a future reviewer doesn't re-open the processor hypothesis without first checking this document.

## Part 3 — Repeatable Validation/Testing Method for Training-Run Outcomes

This section was drafted by `team-code`, then submitted to `@team-finance` for an actual independent trading-desk-credibility review (not simulated) before being finalized. `@team-finance` acknowledged the Priority-0 end-users, pulled the primary evidence itself (re-reading `train_alpha158_lightgbm.py`, the production YAML, the score parquet, and the full `mlruns/` metrics set rather than taking the brief at face value), and returned an **ENDORSED-WITH-CHANGES** verdict. The design below is the *post-review, revised* methodology — team-code's original draft is not reproduced separately; every material change the review required has been folded in directly, with the review's own evidence cited inline.

### 3.1 Design goals

Must have caught, before the score file reached a downstream report:
- The 2026-09-05 degeneracy (1 tree, 1 leaf, 0 splits, IC/RankIC ≈ 0/`nan`).
- The 2026-09-08 degeneracy (1 tree, 31 leaves, IC superficially plausible but RankIC sign-flipped, 7 distinct scores across 903 names, 858 names sharing one value — and, per `@team-finance`'s Finding A (2.1 item 3), this is not a latest-date-only artifact: median distinctness across all ~420 dates in the file is 0.0055, median dominant-share is 0.961 — every date fails).

Per 2.1's table, **IC/RankIC thresholds alone are demonstrably insufficient** — `145fb751`'s IC (0.00718) sits inside the range of the healthy runs. `@team-finance`'s review adds the decisive correction here: the original draft responded to that insufficiency by demoting *all* metrics to secondary and leaning on distinctness alone. That over-corrected. `PortAnaRecord` — already wired into the production YAML's `task.record` list — was already computing portfolio-level metrics (information ratio, annualized return, max drawdown, fill rate) for every run, and those metrics separate the bad run from the healthy runs with **zero distributional overlap** (2.1 item 3's table), at zero marginal computation cost. The corrected design below treats **distinctness and portfolio metrics as co-primary**: distinctness is the check that always runs (needs only the score file, no recorder or backtest required); portfolio metrics are the check that decides (the strongest available signal, in the currency — P&L — an Institutional Hedge Fund Manager actually reads). IC/RankIC remain demoted to secondary, as originally proposed and re-confirmed correct by the review.

### 3.2 Proposed checks (post-review)

1. **Minimum cross-sectional distinctness per date — PRIMARY.**
   - For each date: `n_distinct / n_names` and `dominant_share = max(value_counts) / n_names`.
   - **Revised thresholds** (team-finance correction: the original 0.30/0.20 pair left a dead zone wide enough to admit the next incident — a healthy LightGBM regression ensemble emits effectively-unique float64 scores, so the healthy population sits at `n_distinct/n_names ≈ 1.0` and `dominant_share ≈ 1/n ≈ 0.001`, not near the original floor/ceiling): hard-fail if `n_distinct / n_names < 0.95` **or** `dominant_share > 0.02`.
   - **Revised scope** (team-finance correction, Finding A): hard-fail if this occurs on the most recent date **or** on more than a small fraction of dates in the file — not "warn-only on historical dates" as originally drafted, since the actual incidents were systemic across the whole file, not isolated to the latest date.
   - Verified against both incidents: 2026-09-05 (0.26 distinct) fails the 0.95 floor; 2026-09-08 (0.0055 median, 0.961 median dominant-share) fails both by a very wide margin.
2. **Boosting-round / model-complexity sanity check.**
   - **Revised** (team-finance correction: `num_trees() <= 1` is too permissive — it only catches the exact incident already seen; with `early_stopping_rounds=50` against Qlib's default `num_boost_round=1000`, a healthy run terminates in the hundreds of trees): hard floor `num_trees() >= 50`, plus a non-convergence warning if `num_trees() >= num_boost_round` (i.e. the run hit the round cap without early stopping ever triggering — suspicious on its own).
   - `trained_model.model.num_trees()` is already computed and logged today (`train_alpha158_lightgbm.py` line ~775-776, `"Model Quality Check: num_trees=..."`) — this check is enforcement of existing telemetry that was never acted on, not new instrumentation.
3. **Portfolio metrics (IR / annualized return / max drawdown / fill rate) — CO-PRIMARY. (New — added per `@team-finance` review.)**
   - Sourced from `PortAnaRecord`'s already-logged output (via `qlib/contrib/evaluate.py`'s `risk_analysis()`/`indicator_analysis()`, which `PortAnaRecord` calls internally) — no new computation, no new recorder wiring, this data already exists in `mlruns/` for every run today and is simply never read by the training script.
   - Provisional floors, derived from the healthy-run population in 2.1 item 3's table: information ratio ≥ +0.5, annualized return > 0, max drawdown ≥ -0.20, `ffr` (fill rate) == 1.0 exactly (a fill rate of `nan` — as seen on the bad run — must be treated as an automatic hard fail, not a missing-value skip).
   - This is the single strongest discriminator identified in this review: IR -2.018 vs. a healthy range of +0.674 to +1.495; max drawdown -44.0% vs. a healthy range of -7.1% to -14.2%; no overlap in either case.
4. **IC / RankIC / ICIR sanity bounds — secondary/corroborating (demotion confirmed correct by review).**
   - Source from `SigAnaRecord`'s own logged metrics/`ic.pkl`/`ric.pkl` (per Part 1.4.2's consolidation), not the hand-rolled `calculate_ic_metrics()` duplicate — retire or demote that function to logging-only so two disagreeing IC computations never coexist inside a gate.
   - **Mandatory correctness fix flagged by review**: every numeric comparison here must begin with an explicit `isnan` check and treat NaN as an automatic hard fail in its own right — `nan < floor` evaluates to `False` in Python, so a naively-written bound would have silently *passed* the 2026-09-05 incident (`Rank IC = nan`), the exact artifact this whole check exists to catch.
   - **Mandatory fail-closed fix flagged by review**: at least three runs already in this repo's local `mlruns/` (`6c9dbe04`, `57e93274`, `81c27e3b`) have some or all of these metrics entirely absent, not merely bad. Absence must be treated as failure, never as "nothing to check."
5. **Comparison against a pinned, known-good reference — sequenced last, not against the live production path.**
   - **Critical correction from review**: the original draft proposed diffing the new run against "the currently-deployed production score file." As written, that file is *itself* the corrupt 2026-09-08 artifact (median dominant-share 0.961) — implemented literally, the next healthy retrain would be flagged as an unexplained regime change relative to that corrupt baseline, while future degenerate runs would compare favorably against an already-degenerate one. The baseline must instead be a **pinned, explicitly-blessed, immutable known-good reference artifact**, updated only through a deliberate re-blessing step, never implicitly equal to "whatever currently occupies the production path."
   - **Method correction from review**: rather than diffing summary scalars (distinctness-vs-distinctness, IC-vs-IC), compute **cross-sectional Spearman rank correlation between the candidate and the pinned reference on overlapping `(date, symbol)` pairs**. A legitimate retrain on largely-overlapping history is highly rank-correlated with its predecessor; a structural break shows up as correlation near zero. This uses the joint distribution instead of discarding it.
   - **Sequencing**: this check cannot be turned on until a clean, gate-passing run exists to bless as the pin (see Part 2's follow-up task) — it must be the last check implemented, after checks 1-4 are in place and a healthy artifact has been produced and explicitly blessed.

### 3.3 Additional checks required by the review (not in the original draft)

`@team-finance` identified concrete gaps a real desk would insist on, beyond re-ranking the four checks above. Prioritized:

- **P0 — Override-cannot-write-production, by construction.** This is the control fix, not merely a detector: any hyperparameter override (`--num_boost_round` and any future equivalent) must force output to a scratch/smoke-test path with no flag able to redirect it back to `models/lightgbm/alpha158_russell1000_latest.*` / `output/scores/alpha158_russell1000_latest.*`. This directly closes the mechanism Part 2 confirmed caused the 2026-09-08 incident — the gate in 3.2 detects a bad artifact; this prevents a debug run from ever being in a position to become one. (This corresponds to, and supersedes with a stronger mechanism, the "gate `--num_boost_round` behind an explicit flag" idea in Part 1.4.1.)
- **P0 — Atomic staged promotion, with score-file versioning added.** The review's Finding D: production is currently overwritten at four separate, non-atomic sites in `train_alpha158_model()` (`.pkl` at lines 758-761, `.txt` at 765-771, `.json` at 815-817, `.parquet`/`.csv` at 869-870), model artifacts written well before scores. A gate placed "immediately before the overwrite" is not implementable as a single insertion point today — a failed gate can still leave a bad `.pkl`/`.txt` already in production with only the scores withheld. Promotion needs restructuring: compute the full evidence set (model + scores + all metrics) first, run the gate exactly once against that complete set, and only then write everything, staged to temp paths and moved into place atomically. Additionally: the `.pkl` is already versioned to `models/lightgbm/checkpoints/` (line 823) but `output/scores/alpha158_russell1000_latest.parquet` has no equivalent — there is currently no rollback path for a bad score file, which is exactly the artifact type both real incidents corrupted.
- **P1 — Fail-closed on the two existing silent-failure paths.** `train_alpha158_lightgbm.py` lines 873-874 currently swallow score-export failure into a `logger.warning` and continue (the run reports success with `scores_exported=False` silently dropped from the summary banner); `calculate_ic_metrics()` returns an all-zero dict on both exception and empty-merge, making "the computation broke" indistinguishable from "IC is genuinely ≈0." Both must raise, not warn-and-continue, once the gate is in place — otherwise the worst-case outcome is a replaced `.pkl` paired with a stale, mismatched `.parquet`, reported as a successful run.
- **P1 — Score-file schema/integrity assertions**, cheap and deterministic, no calibration needed: no NaN/inf in `score`; no duplicate `(date, symbol)` rows; row count and per-date universe breadth within tolerance of the reference; the derived `rank`/`percentile` columns (`train_alpha158_lightgbm.py` lines 864-867) internally consistent with `score`.
- **P1 — Staleness/recency assertion.** `max(date)` in the output score file must fall within N business days of the run date. This is a real, currently-live gap unrelated to the two incidents: the production YAML's `test` segment is hardcoded to end `2026-09-04`, and nothing in this pipeline notices when that drifts stale relative to the actual run date.
- **P2 — Provenance stamping.** Record git SHA, a config hash, and the training seed inside `alpha158_russell1000_latest_meta.json` alongside the hyperparameters already captured there — without this, "was this artifact produced by the blessed config?" is unanswerable after the fact, and check 5's pinned reference has nothing durable to pin to.

### 3.4 Where this should live

- **Primary enforcement point: inside `train_alpha158_lightgbm.py` itself**, restructured per 3.3's P0 atomic-promotion fix — compute model, scores, and all metrics first; call a single gate function (e.g. `validate_score_quality(scores_df, ic_metrics, portfolio_metrics, trained_model, pinned_reference=None) -> None`, raising on any hard-fail) exactly once; only on success, write all artifacts via staged temp paths + atomic move. This matches the user's stated preference ("ideally something `train_alpha158_lightgbm.py` itself runs and fails loudly on") and, per the review, is the only placement that can actually prevent promotion rather than merely detect a problem after the fact.
- **The gate function should live in its own module** (e.g. `qlib/contrib/validation/score_quality.py` or `scripts/validate_score_quality.py`), independently importable and invocable against any artifact — including re-checking the artifact currently deployed in production — rather than existing only inline inside the script that contained the original footgun.
- **Secondary: a `tests/` regression test** (`tests/test_train_alpha158_quality_gate.py`, following the exact pattern already established by `tests/test_visualize_key_contracts.py` — real, not mocked, payloads) so the gate's logic is regression-tested without needing a real (slow) training job. Per the review, include **four** fixtures, not two: the 2026-09-05 shape (232/908 distinct, `Rank IC = nan`), the 2026-09-08 shape (7/903 distinct, dominant 858/903, IR -2.018/MDD -44%), a dedicated NaN-RankIC fixture isolating the fail-closed NaN-handling fix in 3.2.4 (since that is the specific trap a naive comparison falls into), and one healthy synthetic fixture (mirroring the `362c9610` baseline's shape) asserted to pass.
- **Not** a CI gate in the GitHub Actions sense — no evidence of a CI pipeline tied to model retraining exists in this repo today. The review's position: an interim pre-push hook or `make` target enforcing `pytest tests/test_train_alpha158_quality_gate.py` is acceptable as a stopgap; indefinite reliance on developer discipline alone is not. If CI is added later, wiring this test in is a one-line addition.
